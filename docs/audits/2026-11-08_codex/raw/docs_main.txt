# Hill Climb harness: design (the contract every file follows)

## What it is

A supervisor that runs Dream-1 through a long-horizon task as a sequence of stages. For each stage it gives
the model a prompt, watches the cameras, decides whether the stage worked, and recovers when it did not.

It never touches a motor. It drives Dream's own station agent (`dreamcli robot up`) through that agent's
HTTP API, so every speed cap, clamp, gripper force cap and home move in Dream's control loop stays in force.

## The two endpoints it uses (both on the station, both 127.0.0.1)

Station agent, started by the person with `dreamcli robot up [joint] --view-port 8093` (default API port 8091).
Routes (from `robots/station_api.py`, dreamlabs 1.0.37):

| Route | Body | Reply |
| --- | --- | --- |
| `GET /status` | | 200, status dict |
| `POST /start` | `{"prompt": str?, "checkpoint": str?}` | 200 status; 409 `{"error"}` when a run exists |
| `POST /stop` | `{}` | 200 status once the arms hold; 409 during a home move |
| `POST /home` | `{}` | 200 once the arms are home; 409 while a run exists |
| `POST /reset` | `{}` | 200 status (reopens a dead arm driver) |
| `POST /prompt` | `{"prompt": str}` | 200 status; 400 without a non-empty prompt. Changes the running task live |

Errors: 400 bad body, 404 route, 409 refused transition, 504 timeout (60 s), 500 other; body `{"error": msg}`.

Status dict keys used: `state` (one of `idle`, `starting`, `running`, `stopping`, `homing`, `resetting`,
`error`), `prompt`, `checkpoint`, `run` (int, run number), `chunks`, `stalls`, `clamps`, `arms`
(`{name: bool alive}`), `cameras` (`{name: age_s or None}`), `last_error` (str or None), `run_elapsed_s`.

Debug view (`--view-port 8093`), from `dream/debug_view.py`:

- `GET /trips` -> JSON list, oldest first, of `{"n": int, "sent_s": float, "error": str|None, "rtt_ms": ...}`.
- `GET /trip/<n>` -> JSON `{"n", "sent_s", "frames": {"video.<role>": [base64 JPEG, ... oldest first]},
  "observation", "action", "timing", "error", "trained"}`; 404 when no longer kept.

The harness reads the newest trip's newest frame per camera as "what the robot sees now".
Camera role keys look like `video.scene`, `video.wrist_l`, `video.wrist_r` (exact names vary by station:
match by substring, config `cameras_for_check` lists which roles a verifier gets, default all).

### station_client.py

```python
class StationError(Exception): ...          # carries .status_code and .message
class StationClient:
    def __init__(self, base_url="http://127.0.0.1:8091", *, timeout_s=70.0, dry_run=False, log=None): ...
    def status(self) -> dict                  # GET /status (allowed in dry run)
    def start(self, prompt: str, checkpoint: str | None = None) -> dict
    def set_prompt(self, prompt: str) -> dict
    def stop(self) -> dict
    def home(self) -> dict
    def reset(self) -> dict
    def wait_for_state(self, states: set[str], timeout_s: float, poll_s=0.5) -> dict  # raises TimeoutError
```

`dry_run=True`: every POST is NOT sent; it logs `"DRY RUN: would POST /start {...}"` and returns the last
real status (or a synthetic `{"state": "running", ...}` when the station is unreachable). GETs are sent.
Uses `urllib.request` only. Non-2xx -> `StationError`.

### frames.py

```python
class FrameSource:
    def __init__(self, base_url="http://127.0.0.1:8093", *, timeout_s=5.0): ...
    def latest(self) -> dict[str, bytes]      # role -> JPEG bytes, newest trip's newest frame per key; {} if none
    def latest_n(self) -> int | None
```
Strips a `video.` prefix from role names. Never raises on network trouble: returns `{}` and remembers the error.

### plan.py (YAML schema)

```yaml
task: "clear the table into the bin"         # overall, for logs
checkpoint: null                              # dream-1-ft:... or null for base Dream-1
time_budget_s: 900                            # whole run
check_every_s: 3.0                            # how often a verifier is asked while a stage runs
verifier: manual                              # default for stages: manual | claude | time
claude: {model: claude-haiku-5-5, max_tokens: 200}
stages:
  - name: pick_red
    prompt: "pick up the red cube"
    success: "Is the red cube held in a gripper, off the table?"   # the yes/no question a verifier answers
    timeout_s: 60
    max_attempts: 3
    min_run_s: 4                                # don't ask a verifier before this
    verifier: manual                            # optional override
    recovery:                                   # tried in order on attempt 2, 3, ... (else the stage prompt again)
      - "open both grippers and move the arms up"
    on_fail: home_and_retry                     # retry_in_place | home_and_retry | skip | abort
```

`load_plan(path) -> Plan` validates: non-empty prompts (<=512 chars, single line), positive times,
`max_attempts>=1`, known enums; raises `ValueError` naming the stage and field.

### verifiers.py

```python
@dataclass
class Verdict: done: bool | None; confidence: float; reason: str   # None = can't tell yet
class Verifier(Protocol):
    def check(self, stage: Stage, frames: dict[str, bytes], elapsed_s: float) -> Verdict: ...
```

- `ManualVerifier(input_stream=sys.stdin)`: a background thread reads lines; `y`=done, `n`=failed now,
  anything else ignored; `check()` returns the latest unread key press as a verdict, else `Verdict(None,...)`.
  Prints the stage question once per stage.
- `ClaudeVerifier(model, api_key from ANTHROPIC_API_KEY, max_tokens)`: POST to
  `https://api.anthropic.com/v1/messages` with headers `x-api-key`, `anthropic-version: 2023-06-01`,
  `content-type: application/json`; content = each camera JPEG as an `image` block (base64, media_type
  image/jpeg) labelled by role, then the text: the stage question + "Answer with JSON only:
  {\"done\": true|false, \"confidence\": 0..1, \"reason\": \"...\"}". Parses the first JSON object in the reply.
  Any error -> `Verdict(None, 0, "verifier error: ...")`. Requires done with confidence >= 0.7 to count.
  Never sends the key anywhere else; never logs it.
- `TimeVerifier`: done once `elapsed_s >= stage.timeout_s * 0.9` (for stages with no check), confidence 0.5.
- `make_verifier(name, plan) -> Verifier`.

### runner.py: the state machine

```python
@dataclass
class StageResult: name: str; ok: bool; attempts: int; seconds: float; reason: str
@dataclass
class RunResult: ok: bool; stages: list[StageResult]; seconds: float; reason: str
class Runner:
    def __init__(self, plan, station: StationClient, frames: FrameSource, verifiers: dict[str, Verifier],
                 log: RunLog, *, clock=time.monotonic, sleep=time.sleep): ...
    def run(self) -> RunResult
    def request_stop(self) -> None            # thread-safe; makes run() stop the station and return
```

Behaviour:
1. Preflight: `status()`. Refuse (RunResult ok=False) if state not in {idle, error}... except state
   `running` is refused too (someone else's run). Refuse if any `arms` value is False or any camera age is
   None or > 2 s. In dry run, report these as warnings and continue.
2. First stage: `start(prompt, plan.checkpoint)`, then `wait_for_state({"running"}, 120)` (a new model can be
   slow; on `error` state stop and fail with `last_error`).
3. Each later stage, if the run is still `running`: `set_prompt(next prompt)` (no stop between stages).
   If the run ended (state idle) start it again with the new prompt.
4. While a stage runs: every `check_every_s`, poll status; if `state == "error"` or an arm is dead -> `stop()`
   and fail the whole run (`abort`). After `min_run_s`, grab `frames.latest()` and ask the stage's verifier.
   `done True` -> stage ok, next stage. `done False` (manual `n`) -> attempt failed.
   `elapsed >= timeout_s` -> attempt failed.
5. Attempt failed: if attempts < max_attempts: by `on_fail`:
   - `retry_in_place`: `set_prompt(recovery[i] if any else prompt)`; for a recovery prompt, run it for
     `min(timeout_s/2, 20)` s, then `set_prompt(prompt)` again and restart the stage clock.
   - `home_and_retry`: `stop()`, wait idle, `home()`, wait idle, `start(prompt)`.
   - `skip`: mark failed, go to next stage. `abort`: stop and fail the run.
   Out of attempts: `skip` behaviour if on_fail is `skip`, else fail the run.
6. Whole-run `time_budget_s` exceeded -> stop, fail. `request_stop()` or KeyboardInterrupt -> `stop()` then
   return. After the last stage: `stop()` (the arms hold; the person homes them).
7. Every decision goes to the log.

### log.py

`RunLog(dir)`: creates `runs/<UTC timestamp>/`, writes `events.jsonl` (`{"t", "event", ...}` per line),
`save_frames(tag, frames)` writes `<seq>_<tag>_<role>.jpg`, and `summary.json` at the end.

### cli.py (`python -m harness`)

```
python -m harness plans/x.yaml --dry-run          # reads status/frames, sends nothing that moves an arm
python -m harness plans/x.yaml --live              # real; asks the person to type "yes" first
python -m harness plans/x.yaml --mock              # starts fake_station in-process, no station needed
  --station http://127.0.0.1:8091 --view http://127.0.0.1:8093 --runs-dir runs
```
Exactly one of `--dry-run`, `--live`, `--mock` is required. `--live` prints the safety lines (hand on the
e-stop, people clear) and requires typing `yes`. Ctrl+C at any time -> `POST /stop` then exit.
`s` + Enter in the terminal while running also stops (shares the stdin reader with ManualVerifier).

## fake_station.py (offline stand-in)

`FakeStation(api_port=0, view_port=0, *, scenario="happy")`: two `ThreadingHTTPServer`s on 127.0.0.1
implementing exactly the routes above, with the real state machine (idle -> starting -> running; stop ->
stopping -> idle; home -> homing -> idle; 409s for refused transitions), a growing `chunks` count, trip list
with synthetic JPEG frames (a tiny valid JPEG constant; roles `video.scene`, `video.wrist_l`, `video.wrist_r`)
whose observation carries the current prompt. `.api_url`, `.view_url`, `.start()`, `.close()`, `.calls`
(list of `(method, route, body)`). Scenarios: `happy`; `arm_dies` (an arm goes False 3 s into the run);
`start_error` (start -> error state with last_error); `slow_start` (5 s in starting); `camera_stale`.
Also `fake_station.FakeVerifier(script: dict[stage_name, list[Verdict|None]])` returning scripted verdicts.
Runnable alone: `python fake_station.py` serves on 8091/8093.

# Harness v2: changes backed by the Hill Climb reading list

Everything in DESIGN.md still holds unless changed here. Backward compatible: v1 plans still load and run
the same way (all new fields optional with defaults that reproduce v1).

Sources: the event prep guide; Sentinel (runtime monitoring), FLARE
(retry vs reset recovery), Hi Robot (hierarchical high level), SARM (stage-aware progress), Robometer
(progress dynamics), RTC and DreamZero (latency / prompt-change delay), IWR and RECAP (data loop).

## 1. A monitor, not a yes/no checker (Sentinel, SARM, Robometer, Hi Robot)

New verifier `monitor` (`verifiers.MonitorVerifier`), Claude-backed. Per call it sends:
- a frame **history**, not one image: the stage's first overhead frame + the last `history_frames` (default 6)
  overhead frames kept from earlier checks (oldest first), + the newest wrist frames. Images labelled
  ("t=+12s overhead", ...). Single-image QA mostly cries failure (Sentinel: TNR <= 7%).
- text: the overall task, the full stage list with the current one marked, the stage's `success` question,
  `expect` (optional, what correct behaviour looks like), elapsed seconds in the stage and its `timeout_s`,
  the last prompt sent to the robot, the stage's recovery menu (name + `when`), and this instruction:
  "First write 2-4 short questions about the robot and objects that decide this, and answer them from the
  images. Do not call the stage failing unless it is unlikely to finish within the time left. Then output
  JSON only between <json> and </json>:"
  `{"stage_done": bool, "progress": 0..1, "status": "ok"|"stalled"|"failing", "holding": {"left": str, "right": str},
    "recovery": <index into the recovery menu or null>, "scene_ok": bool, "confidence": 0..1, "reason": str}`
- Parsing: take the text between the markers; on any error return `MonitorVerdict(done=None, ...)`.
  Validate: `recovery` must be null or a valid index; clamp numbers.
- Runs **asynchronously**: the runner keeps polling status while a call is in flight (a background thread,
  at most one call in flight; results are consumed by the next tick). Calls take seconds (Sentinel: 14 s mean
  on GPT-4o), and a blocking call would starve health checks.

`MonitorVerdict(Verdict)` adds `progress: float|None`, `status: str|None`, `recovery: int|None`,
`scene_ok: bool|None`, `holding: dict|None`. Other verifiers return plain `Verdict` (treated as status None).

## 2. Debounced decisions (Sentinel, prep guide "false success is expensive")

Plan-level `confirm` (default 1 = v1 behaviour; recommend 2 with monitor):
- a stage succeeds only after `confirm` consecutive `done True` verdicts (manual `y` counts as confirmed at once);
- a monitor `status: failing` ends the attempt only after `confirm` consecutive failing verdicts AND elapsed
  >= 50% of `timeout_s` (manual `n` stays immediate);
- verdicts with no frames (empty dict) are never counted as success (missing data can't pass).

## 3. Stall detection from progress dynamics (Robometer, SARM)

Stage field `stall_s` (default null = off). If the monitor reports progress, keep the max progress seen in
the attempt; if it has not risen by >= 0.05 for `stall_s` seconds, or the monitor says `stalled` `confirm`
times in a row, the attempt fails with reason "stalled". A drop of >= 0.3 below the attempt's max
(regression, e.g. object dropped) logs a `regression` event and counts as a failing verdict.

## 4. Recovery menu with applicability, chosen from a closed set (FLARE, Hi Robot)

Stage `recovery` items may be a string (v1) or a mapping:
`{name, prompt, when, kind: retry|reset, settle_s (default 8), max_uses (default 1)}`.
- `kind: retry` = environment still on the task path: just re-issue the stage prompt (FLARE ID error).
- `kind: reset` = scene broken (toppled/dropped/stuck object): send the recovery prompt, run it for
  `settle_s`..`min(timeout_s/2, 20)` s, then ask the verifier for `scene_ok` (monitor) before re-issuing the
  stage prompt; if the scene is still not ok, that counts as another failed attempt.
- Selection on a failed attempt: the monitor's `recovery` index if it gave one and that item still has uses
  left; else the next unused item in list order; never the same item twice in a row; when none is left, fall
  back to `on_fail`.

## 5. Prompt-change settle time (DreamZero, RTC)

Stage `settle_s` (default = `min_run_s`): after any prompt change no verifier is asked and no stall clock
runs. A VLA executes the chunk already in flight and DreamZero-style models keep ~seconds of visual context,
so the old prompt lingers. Log `prompt_change` events with the status `chunks` count, and log the first
check where the monitor's `progress` moved, so the delay can be measured on the station.

## 6. Entry check (prep guide "entry conditions")

Stage `skip_if_done` (default false): before sending a stage's prompt, ask the verifier once; if it says done
with confidence >= 0.8 (monitor) or the operator typed y, record the stage ok with 0 attempts and move on.

## 7. Data loop and evaluation (IWR, RECAP, SARM, prep guide)

- `runs/<ts>/segments.jsonl`: one line per stage attempt and per recovery: `{stage, attempt, kind:
  stage|recovery, prompt, t_start, t_end (epoch s), outcome, reason, max_progress}`. These line up with
  Dream's own rollout recordings by wall clock, so successful stage segments can be cut out for fine-tuning
  and failed ones excluded (SARM drops negative-progress data; IWR keeps the policy's own data around
  corrections).
- `runs/<ts>/manifest.json`: plan file path + sha256, harness version, station status at start (checkpoint,
  prompt), CLI args, host, start/end time.
- `python -m harness.report runs/ [--last N]`: a table over runs: run ok, stages ok/total, per-stage success
  rate, mean attempts, mean seconds, recoveries used and their success rate, most common failure reasons.
  Also counts "false success" when a stage after a successful one fails immediately with
  `scene_ok false` (a lead, not proof).

## 8. Small things

- `MonitorVerifier` model default `claude-haiku-5-5`; plan `claude.model` overrides; `max_tokens` default 4000 (was 600; it cut off every Haiku 5.5 reply)
  (the questions need room).
- CLI `--verifier` accepts `monitor` and `monitor+manual` (operator key wins, like claude+manual).
- `ClaudeVerifier` (v1) unchanged.
- All new behaviour has tests against fake_station with a scripted fake monitor (no network).

# Hill Climb harness

A supervisor that runs Dream-1 through a long-horizon task as a sequence of stages. For each stage it
gives the model a prompt, watches the cameras, decides whether the stage worked, and recovers (re-prompt,
home and retry, skip, or abort) when it did not. Every decision goes to `runs/<timestamp>/events.jsonl`
with the camera frames it looked at.

Python 3.12+, stdlib + PyYAML only. The design contract is `DESIGN.md`.

## Status (8 Nov 2026)

Tougher in simulation, not yet proven on the real table. Read [last night's report](docs/LAST_NIGHT_2026-11-08.md) for
the results, Dream errors, the open tower-order question, Darsh's strategy notes and the data still to collect. His
notes are coded on branch `cloud-sims`, not on `main` yet.

## Safety model

- **It never touches a motor.** It has no robot driver, no joint commands, no camera drivers. It only
  calls Dream's own station agent over HTTP on 127.0.0.1 (`/status`, `/start`, `/stop`, `/home`, `/reset`,
  `/prompt`) and reads frames from the debug view. Every speed cap, clamp, gripper force cap and home move
  stays in Dream's control loop.
- **Preflight refuses** to start if the station is not idle, an arm is dead, or a camera is stale (> 2 s).
- **Fails safe**: an arm dying, the station entering `error`, the time budget, Ctrl+C, or `s` + Enter all
  send `POST /stop` (the arms hold where they are). It never homes at the end; you do that.
- `--dry-run` sends no POST at all; `--live` makes you type `yes` after the safety lines.
- The physical e-stop is still the real safety. Keep your hand on it.

## Run it (on the station)

```bash
source ~/dream-env/bin/activate
dreamcli robot up --view-port 8093            # Metal fine-tune too; a YAM fine-tune: dreamcli robot up joint ...

python -m harness plans/example_hill_climb.yaml --dry-run    # reads status/frames, prints what it would POST
python -m harness plans/example_hill_climb.yaml --live       # hand on the e-stop, people clear; type yes

dreamcli robot down                                          # at the end
```

Keep the `dreamcli robot up` terminal running; run the harness in a second terminal (also with the
`dream-env` activated). Options: `--station URL` (default `http://127.0.0.1:8091`), `--view URL`
(default `http://127.0.0.1:8093`), `--runs-dir DIR`, `--verifier manual|claude|time` (override every stage).

While running, type `y` / `n` + Enter to answer a manual verifier, `s` + Enter to stop.

Offline practice, no station needed: `python -m harness plans/example_hill_climb.yaml --mock
[--scenario happy|arm_dies|start_error|slow_start|camera_stale]` (uses `fake_station.py`). Manual stages
wait for your keypresses; add `--verifier time` to let it run unattended.

## Test in simulation

`sim_station.py` is a stand-in for the station agent that drives Dream's own MuJoCo YAM simulator
(`dream_examples/yam_mujoco`), with the same HTTP routes on 8091 and the same debug view on 8093. The harness
cannot tell the difference, so you can test a plan end to end, with the real Dream-1 model, before the robot.
It uses Dream's own control loop (camera windows, `get_action`, `validate_chunk`, 20 Hz stepping), so nothing
physical is involved and `--live` is safe to confirm.

On a laptop with the `dreamlabs` library installed and your Dream API key saved (`~/.dreamlabs/credentials`,
from the Getting started page):

```bash
# terminal 1: the simulated station (real Dream-1, real time)
python sim_station.py --policy dream [--checkpoint dream-1-ft:...]

# terminal 2: the harness against it
python -m harness plans/sim_fruit_bowl.yaml --live --station http://127.0.0.1:8091 --view http://127.0.0.1:8093
```

`plans/sim_fruit_bowl.yaml` has three stages for objects in the sim scene (apple, orange, banana, a bowl and a
blue plate). The verifier is `manual`: watch the saved frames in `runs/<timestamp>/` or the `/trip/<n>` frames
on 8093, or run with `--verifier time` to let it run unattended. If Dream's example is not under
site-packages, add `--example-dir PATH/TO/dream_examples/yam_mujoco`. `--no-realtime` runs the sim as fast as it
renders.

Offline, no key and no network: `python sim_station.py --policy scripted` returns small sinusoidal joint chunks
of the right shape, so the harness, the state machine and the frames can be tested anywhere that has
`pip install mujoco pillow numpy`. On a headless Linux box set `MUJOCO_GL=egl` (needs a GPU) or
`MUJOCO_GL=osmesa` (software; `apt install libosmesa6`), which is the automatic default there. Software
rendering is slow (about 5 s per chunk), so use long stage timeouts or `--verifier time`.
`pytest tests/test_sim_station.py` covers the scripted mode and skips itself without mujoco.

Watching it live: the view port serves `/live` (the three policy cameras, a ground-truth top-down map, the
referee on `--scene hill_climb`, station state and the last policy round trips; `--open` opens it), and
`--viewer` opens MuJoCo's own 3D window with a status overlay (macOS: start it with `mjpython`, not `python`).
`python experiments/live_stress.py -s SCENARIO --speed 10` plays an offline stress match in the browser at 10x
(table, stages, harness decisions, live score), and `experiments/sweep_variants.py` A/Bs plan and harness
variants over every stress scenario at a given monitor latency (`--latency 6.5-13` is what Haiku 5.5 measured).

## Match plan and the fine-tune

`plans/hill_climb_v4.yaml` is the match plan for rubric v4. Its prompts are the six task texts in
`TELEOP_PLAN.md`, the texts the fine-tune is recorded with. Check that a plan's prompts all have demos:

```bash
python -m harness.tasks plans/hill_climb_v4.yaml ~/hackathon_data/unplug-v1 ~/hackathon_data/relay-v1
```

It also has a black-ball `guard:`. On every ball check the monitor answers "is a gripper holding a black 8-ball?",
and a yes stops the run at once, with the ball still held (HARNESS_GUIDE.md section 6d).

## Writing a plan

```yaml
task: "clear the table into the bin"      # for logs
checkpoint: null                           # dream-1-ft:... or null for base Dream-1
time_budget_s: 900                         # whole run
check_every_s: 3.0                         # how often a verifier is asked
verifier: manual                           # default: manual | claude | time
cameras_for_check: [scene]                 # optional: roles a verifier sees (substring match), default all
stages:
  - name: pick_red                         # unique
    prompt: "pick up the red cube"         # one line, <= 512 chars; sent to the model as-is
    success: "Is the red cube held in a gripper, off the table?"   # yes/no question for the verifier
    timeout_s: 60                          # attempt fails after this
    max_attempts: 3
    min_run_s: 4                           # no verifier call before this
    verifier: manual                       # optional per-stage override
    recovery:                              # prompts tried in order on attempt 2, 3, ...
      - "open both grippers and move the arms up"
    on_fail: home_and_retry                # retry_in_place (default) | home_and_retry | skip | abort
```

Stages run back to back; between stages the harness changes the prompt live (`/prompt`) with no stop.
`retry_in_place` runs the recovery prompt for `min(timeout_s/2, 20)` s and then the stage prompt again;
`home_and_retry` does stop, home, start. Out of attempts: `skip` moves on, anything else fails the run.
Bad plans are rejected with the stage and field named.

## Verifiers

- `manual` (default): you watch the robot; `y` = stage done, `n` = attempt failed now.
- `time`: for stages with no check; done after 90% of `timeout_s`.
- `claude` (optional): sends the camera frames and the stage question to the Anthropic API
  (`claude-haiku-5-5` by default) and needs `ANTHROPIC_API_KEY` in the environment. The key is only sent to
  api.anthropic.com and is never logged or printed. A stage counts as done only for `done: true` with
  confidence >= 0.7. **Using an external model as a judge may not be allowed by the event rules. Check with
  the organizers before using it.** Use `manual` if unsure.

- `claude+manual`: Claude judges every check, and your `y` / `n` overrules it. Run with
  `--verifier claude+manual`. Good for practice runs: you watch Claude's calls in `events.jsonl` and correct them.

No API key? `--claude-backend subscription` (or `HARNESS_CLAUDE_BACKEND=subscription`) sends the same request
(images, prompt, model, effort) through the Claude Code CLI, `claude -p`, on the Claude subscription it is logged
in to (`claude`, then `/login`): no tools, no MCP, no saved session, `ANTHROPIC_API_KEY` removed from its
