# Hill Climb harness: how to use it

The harness runs Dream-1 through a long task as a list of stages. For each stage it:

1. sends a prompt,
2. watches the cameras,
3. decides whether the stage worked,
4. recovers when it didn't.

Version 0.2.0. The design contracts are `DESIGN.md` (v1) and `DESIGN_v2.md` (v2). The short reference is `README.md`.

## 1. What it is, and what it never does

- **It never touches a motor.** It only talks to Dream's own station agent (`dreamcli robot up`) over HTTP on 127.0.0.1:
  - `/status`, `/start`, `/stop`, `/home`, `/reset`, `/prompt` on port 8091
  - the frames from the debug view on port 8093 (`/trips`, `/trip/<n>`)

  Every speed cap, clamp, gripper force cap and home move stays inside Dream's control loop.
- **Preflight refuses to start** if:
  - the station is not idle (or is in error),
  - an arm is dead,
  - a camera is older than 2 s.
- **It fails safe.** Each of these sends `POST /stop`, and the arms hold where they are:
  - an arm dies
  - the station goes into `error`
  - the time budget runs out
  - Ctrl+C
  - `s` + Enter
- It never homes the arms at the end. You do that yourself.
- The physical e-stop is still the real safety. Keep a hand on it during `--live` runs.

## 2. Install

Python 3.12 or newer. The harness needs only PyYAML. On the station, the `dream-env` already has it.

```bash
unzip hill_climb_harness.zip && cd hill_climb_harness
pip install pyyaml pytest             # pytest only for the tests
python -m pytest -q                   # offline, against fake_station.py
```

## 3. Where to run it

**Option A: on the station.** This needs two terminals, both with `source ~/dream-env/bin/activate`.

```bash
# terminal 1: Dream's station agent (leave it running)
dreamcli robot up --view-port 8093          # YAM fine-tune: dreamcli robot up joint --view-port 8093

# terminal 2: the harness
python -m harness plans/<plan>.yaml --dry-run
python -m harness plans/<plan>.yaml --live
```

**Option B: on your laptop, through an SSH tunnel to the station or NUC.** The station agent still runs on the station. The laptop only sends HTTP through the tunnel.

```bash
ssh -L 8091:localhost:8091 -L 8093:localhost:8093 <user>@<station-ip>
# in another laptop terminal:
python -m harness plans/<plan>.yaml --dry-run      # then --live
```

Both endpoints listen on 127.0.0.1 on the station, so the tunnel is the only way to reach them from outside. If you also want the dashboard, add `-L 8080:localhost:8080`.

## 4. The three modes (exactly one is required)

| Mode | What it does |
| --- | --- |
| `--dry-run` | Reads status and frames, and prints every POST it *would* send. It sends nothing that moves an arm. Always do this first on a new station. |
| `--live` | The real run. It prints the safety lines (hand on the e-stop, people clear) and waits until you type `yes`. |
| `--mock` | Starts `fake_station.py` in-process, so no station is needed. Add `--scenario happy\|arm_dies\|start_error\|slow_start\|camera_stale` to practise failure handling. |

Other options:

- `--station URL` (default `http://127.0.0.1:8091`)
- `--view URL` (default `http://127.0.0.1:8093`)
- `--runs-dir DIR` (default `runs`)
- `--verifier NAME` overrides every stage's verifier.
- `--var NAME=VALUE` fills a `{NAME}` placeholder in the plan, for example `--var watch_arm=right`. It can be repeated.

While it runs, type `y` / `n` + Enter to answer a manual check, or `s` + Enter to stop.

## 5. Verifiers (who decides "stage done")

| Name | How it decides | Needs |
| --- | --- | --- |
| `manual` | You watch. `y` means the stage is done. `n` means the attempt failed now. | nothing |
| `time` | Done at 90% of `timeout_s`. Use it for stages with no check, or for unattended practice. | nothing |
| `claude` | Sends one frame per camera and the stage's yes/no question. It counts as done only at confidence >= 0.7. | `ANTHROPIC_API_KEY` |
| `claude+manual` | Same as `claude`, but your `y` / `n` overrules it at once. | `ANTHROPIC_API_KEY` |
| `monitor` | The v2 monitor. It sends a frame **history** (the stage's first overhead frame, the last `history_frames` overhead frames, and the newest wrist frames) with the elapsed time, the timeout, the stage list and the recovery menu. It first writes a few questions about the scene and answers them, then returns JSON: `stage_done`, `progress` 0..1, `status` ok/stalled/failing, `holding` left/right, `recovery` index, `scene_ok`, `confidence`. It runs in the background so health checks keep going. | `ANTHROPIC_API_KEY` |
| `monitor+manual` | Same as `monitor`, but your key press wins. This is the recommended choice for practice runs. | `ANTHROPIC_API_KEY` |

The API key is only sent to api.anthropic.com and is never logged. The default model is `claude-haiku-5-5`, and `claude.model` in the plan changes it.

**Rules:** human `y`/`n` is banned in a match (see 6b). Use `manual` and `monitor+manual` only in practice.

## 6. Writing a plan (YAML)

### Plan-level fields

```yaml
task: "stack the cubes, insert the pegs, plug in the cables"   # for logs and the monitor
checkpoint: null            # dream-1-ft:... for your fine-tune, null for base Dream-1
time_budget_s: 900          # whole run; exceeded -> stop, fail
check_every_s: 3.0          # how often the verifier is asked
verifier: monitor+manual    # default for stages
confirm: 2                  # v2: consecutive "done" (or "failing") verdicts needed; 1 = v1 behaviour
cameras_for_check: [scene]  # optional: camera roles the verifier sees (substring match), default all
claude: {model: claude-haiku-5-5, max_tokens: 600, history_frames: 6}
```

### Stage fields

```yaml
stages:
  - name: pick_blue                      # unique
    prompt: "pick up the blue cube"      # one line, <= 512 chars, sent to Dream-1 as-is
    success: "Is the blue cube held in a gripper, off the table?"   # the yes/no question
    expect: "The arm closes on the cube and lifts it."              # v2, optional, helps the monitor
    timeout_s: 60                        # an attempt fails after this
    max_attempts: 3
    min_run_s: 4                         # no check before this
    settle_s: 6                          # v2: after any prompt change, no check and no stall clock
    stall_s: 15                          # v2: fail "stalled" if progress hasn't risen 0.05 in 15 s
    skip_if_done: false                  # v2: check once before prompting; already done -> skip
    verifier: manual                     # optional per-stage override
    recovery:                            # see below
      - name: keep_going
        kind: retry                      # scene is fine: just re-issue the stage prompt
        when: "the arm is still near the cube"
        max_uses: 2
      - name: reopen_and_lift
        kind: reset                      # scene broken: run this prompt, check scene_ok, then retry
        prompt: "open both grippers and move the arms up"
        when: "the cube was dropped or knocked over"
        settle_s: 8
      - "move the arm back above the cube"   # a plain v1 string still works
    on_fail: retry_in_place              # retry_in_place | home_and_retry | skip | abort | abandon
```

### How a run flows

- **Starting.** The first stage starts the run. Each later stage changes the prompt live (`/prompt`), with no stop in between. If the station goes idle, a match plan ends. Other plans can start a new run.
- **When an attempt fails,** the harness picks the next recovery:
  - the monitor's suggestion, if that item still has uses left;
  - otherwise the next unused item;
  - never the same item twice in a row.

  When the menu is used up, `on_fail` takes over:
  - `retry_in_place` runs the recovery prompt, then the stage prompt again.
  - `home_and_retry` does stop, home, start.
  - `skip` marks the stage failed and moves on after the first failure.
  - `abort` stops the run after the first failure.
  - `abandon` retries within `max_attempts` and `stage_budget_s`, then records optional work as abandoned and proceeds to the next eligible stage.

  `stage_budget_s` includes retries, recovery, and verification. An optional stage can use `reserve_after_s` to leave time for later work.
- **Rules from the papers:**
  - Ask for at least 2 confirmations (`confirm: 2`) before accepting a success. A false success is expensive.
  - A "failing" verdict only counts after 50% of the timeout.
  - A progress drop of 0.3 or more is logged as a regression and counts as a failing verdict.
- **Writing prompts:** keep each prompt atomic, with one object and one action. If the model needs to know which hand to use, name it ("with the left arm").
- **Validation:** a bad plan is rejected before anything runs, and the error names the stage and the field.

## 6b. Match rules and how the plans follow them

Rubric v4 gives each team five minutes. The stages are ordered.

1. **Unplug.** One cable out passes the stage and scores +10. Further unplugs score +5 each. Each originally loose cable plugged into a free port scores +20, up to four.
2. **Stack.** The pass bar is four inches and three seconds of standing freely after release. The scoring table awards +20 for a tower over four inches, +3 per full inch remaining at the end if the stage passed, and +10 for the taller qualifying tower in head-to-head matches.
3. **Balls.** Each shared golf ball resting in our bin at the end scores +5. Either black 8-ball in our bin loses the match.

The rubric awards +10 for LiveKit and +5 for Dimensional when the team shows its use to the referee before the match.

What the rules mean for the harness:

- **No human input after "go".** In a match, use only `verifier: monitor` (the plans set it). Typing `y`/`n` is human input and gets you DQ'd, so never use `manual` or `monitor+manual` in a match. Don't use `time` either: it would move on without the pass bar being met.
- **A false "done" is a DQ.** Touching a later stage's objects before the pass bar is met is a DQ. That's why the plans:
  - require `confirm: 2`,
  - end the run if a required stage exhausts its allocation,
  - ask for fresh evidence of a stack at least four inches tall, stable for three seconds after release.
- The sprint plan ends after the stack. The full plan attempts optional points within its allocations. The designated team member can call stop.
- The match budget is 300 s. After preflight, the runner allocates up to 295 s for work and reserves the final 5 s for requesting stop. The full plan preserves 173 s for clearance and stack while attempting the optional plug. It stops chasing balls after the first unverified count.

See [the match design](MATCH_DESIGN.md) for timing, simulator coverage, and the LiveKit training and observation paths.

```bash
python -m harness plans/hill_climb_sprint.yaml --live
python -m harness plans/hill_climb_full.yaml --live
```

## 6c. A watcher arm for the cable plug-in (second camera view)

The overhead camera is poor at depth, so it can't tell whether a plug is lined up with the port or pushed in. In `hill_climb_full.yaml`, the plug-in has three stages:

1. `watcher_into_place` asks Dream-1 to park the other arm beside the hub. The monitor uses new overhead and watcher-wrist frames to check that the wrist can see a free port from the side.
2. `plug_loose_cable` starts only after the watcher pose passes. The monitor checks that the plug is seated and the watcher still sees the port. It gets the history of both views and the latest working-wrist frame when available.
3. `release_before_stack` opens both grippers and lifts the arms clear before the stack.

You choose the arms with `--var work_arm=left --var watch_arm=right --var work_cam=wrist_l --var watch_cam=wrist_r`. The defaults are: right arm works, left arm watches.

The new stage fields work in any plan:

| Field | What it does |
| --- | --- |
| `cameras` | The camera roles this stage's checks see. This overrides the plan's `cameras_for_check`. |
| `history_cameras` | Extra roles whose frame history the monitor keeps. |
| `camera_notes` | Maps a role to a sentence telling the monitor what that view shows. |
| `required_cameras` | Every verification check needs these views from a distinct camera trip for the current prompt. Use a visual verifier. |
| `requires_stage` | Skip this stage if the named earlier stage did not pass. |

Plans can also set defaults with `vars:`. `--var` overrides them.

Dream-1 controls the watcher pose from the prompt. If the watcher never gets into position, the plan skips the optional plug-in and proceeds to clearing the workspace for stacking.

### Inspect the watcher through DimOS

On Linux or WSL, install the optional dependencies into a Python 3.12 environment and run the viewer from this checkout.

```bash
uv pip install 'dimos[web]==0.0.15' 'langchain-core>=1.2.22,<2'
python -m dimos_skills
```

Connect an MCP client to `http://127.0.0.1:9990/mcp` and call `inspect_watcher` with `arm` set to `left` or `right`. It returns the current station status and labelled JPEGs for the overhead and selected wrist when the latest camera trip matches the active prompt. Use `--station` and `--view` if the simulator uses different ports. This skill reads the station and debug view over HTTP.

### Observe a stage through LiveKit

Install `livekit==1.2.1` and `pillow` in the harness environment. Set `LIVEKIT_URL` and `LIVEKIT_TOKEN` for the station's room. Use a room token with `canSubscribe` enabled and `canPublish` and `canPublishData` disabled.

```bash
python -m harness.livekit_observer --publisher metal-station \
  --track overhead=table_top --track wrist_l=left_wrist \
  --plan plans/hill_climb_full.yaml --stage watcher_into_place
```

Use the publisher identity and exact video track names from the room. With a plan and stage, the observer uses the existing Anthropic monitor and `ANTHROPIC_API_KEY`. Omit both options to capture camera evidence alone. It writes camera JPEGs and optional advisory verdicts under `runs_livekit/`. The logged receive age measures time since the local subscriber received each frame. The RTC timestamp is stored separately. The observer reports on the selected stage while the runner continues to verify its own stage transitions.

## 7. Test in simulation (before the robot)

`sim_station.py` serves the same API (8091) and debug view (8093), driven by Dream's MuJoCo YAM simulator (`dream_examples/yam_mujoco`). The harness can't tell it apart from a real station, and nothing physical moves, so `--live` is safe here. Note that the Hill Climb uses Metal arms, while the sim is YAM only. That makes it a test of the harness logic and prompts, not of the real task.

```bash
pip install dreamlabs mujoco pillow numpy pyyaml
# Dream key: save it once in ~/.dreamlabs/credentials (Windows: %USERPROFILE%\.dreamlabs\credentials)
#   as the block from platform.dreamlabs.ai/setup-api, e.g. a line  DREAM_API_KEY=...
#   or set the DREAM_API_KEY environment variable. Never paste it into a chat.

# terminal 1: simulated station with the real Dream-1
python sim_station.py --policy dream [--checkpoint dream-1-ft:...]
# terminal 2:
python -m harness plans/sim_fruit_bowl.yaml --live --verifier time
```

- **No key or no network:** `python sim_station.py --policy scripted` sends small fake joint chunks of the right shape. It tests the state machine, frames and logs.
- **sim_station.py options:**
  - `--no-realtime` runs the sim as fast as it renders.
  - `--example-dir PATH` points at the Dream example if it isn't installed.
  - `--actions N` sets the rows executed per chunk, 1 to 48.
- **Headless Linux:** set `MUJOCO_GL=egl` (needs a GPU) or `MUJOCO_GL=osmesa`. osmesa is slow, about 5 s per chunk.

## 8. Logs, data and the report

Each run writes `runs/<UTC timestamp>/`:

| File | What it holds |
| --- | --- |
| `events.jsonl` | Every decision, one JSON event per line. This includes `prompt_change` events (with the chunk count) and the first check where progress moved, so you can measure prompt lag. |
| `<seq>_<tag>_<role>.jpg` | The frames each check looked at |
| `segments.jsonl` | One line per stage attempt and per recovery: stage, attempt, kind, prompt, wall-clock start/end, outcome, reason, max progress. These line up by time with Dream's own recordings, so you can cut out successful segments for fine-tuning and drop failed ones. |
| `manifest.json` | Plan path and sha256, harness version, station status at start, CLI args, host, start/end time |
| `summary.json` | The final result |

To compare runs:

```bash
python -m harness.report runs/ [--last N]
```

The report gives:

- run success, and stages ok out of total
- per-stage success rate, mean attempts and mean seconds
- recovery use and how often each recovery worked
- the most common failure reasons
- a "possible false success" count, as a lead rather than proof

## 8b. How hard is it pulling? (`python -m harness.force`)

No firmware change is needed to see the force, and none is needed to change it. On a Metal arm, the force comes from Dream's host software (dreamlabs 1.0.37, `robots/metal.py`), which runs each joint motor in Damiao MIT mode:

> torque = kp × (target − angle) − kd × velocity + gravity feedforward

The gains, from base to wrist:

| | Joints 1–3 | Joint 4 (wrist flex) | Joints 5–6 (wrist yaw, roll) | Gripper |
| --- | --- | --- | --- | --- |
| kp (N·m/rad) | 100 | 50 | 20 | 20 |
| kd | 5 | 5 | 0.6 | 0.6 |

Three things in the station config cap the force:
- the gripper's squeeze, `gripper_hold_torque_nm`: 0.1–2.0 N·m at the motor, 0.5 by default;
- the loop's `grip_force_cap` (0.65);
- the speed and step clamps (`max_ee_speed_m_s` 0.6), which stop the target from running far ahead of the hand.

None of these is firmware, and they belong to the station. Ask Dream's staff before changing them.

After an attempt, copy Dream's trace `~/.dreamlabs/last-run.csv` off the station. It has one row per tick, with the measured and commanded angles of every joint and the gripper. Then run:

```bash
python -m harness.force last-run.csv --arm r --from 12 --to 20 [--tcp 0 0 0.12] [--hold-torque 0.5] [--csv out.csv]
```

It prints:
- the PD torque per joint, and its share of each motor's MIT torque scale;
- the force at the hand, through the arm's Jacobian;
- the gripper's squeeze, and how often it sits at the hold limit;
- the share of ticks that were clamped;
- a reading of which limit you hit:
  - **the grip:** the cable slips in the jaws;
  - **the clamps:** the target can't lead the hand far enough;
  - **the model:** it simply isn't asking for a hard pull. The fix is demos that pull harder.

It's an estimate. The trace doesn't keep measured torque or current, and the tool point defaults to the wrist-roll joint, so pass `--tcp` for the jaw tip.

### Measured torque: `python -m harness.can_torque`

Every Damiao motor answers each command with a state frame: position, velocity, torque (its own estimate from current) and temperatures. Dream's driver reads these frames, but neither its HTTP API nor its trace exposes the torque, so the harness can't read it through Dream. You can still listen passively on the station's CAN link while a run goes. This never sends a frame:

```bash
ip -details -brief link show type can                 # are the arms on SocketCAN links (can_left / can_right)?
candump -L -n 4000 can_right > right.log              # listen only, during an attempt
python -m harness.can_torque right.log [--csv out.csv]
```

It prints per joint: the median and peak torque, its share of the motor's torque scale, the peak temperature and any fault frames. Only the gripper row tells you the squeeze directly.

If the adapters are CANables in slcan mode (a `/dev/tty…` serial device), the port is exclusive to Dream's agent and can't be listened to. In that case, use `harness.force` on the trace instead.

## 9. Checklist on the day

1. `python -m pytest -q` passes. Then run `--mock --scenario arm_dies` once to watch it stop safely.
2. Run `dreamcli robot up --view-port 8093` on the station. Check that `curl -s localhost:8091/status` shows `idle`, both arms alive, and cameras fresh.
3. `--dry-run` with your plan: check the printed POSTs and that the frames arrive (`runs/.../*.jpg`).
4. `--live` with `monitor+manual` or `manual`, a hand on the e-stop and people clear. Correct the monitor with `y`/`n`.
5. After each run, read `python -m harness.report runs/`. Tune prompts, timeouts and recoveries, and keep the good segments for the fine-tune.
6. At the end: home the arms yourself, then `dreamcli robot down`.

# Five-minute Hill Climb supervisor

## Usage

Run the sprint plan for unplug and stack, or the full plan to exercise the optional plug and balls. Use a mock station and a scripted monitor for scheduling tests.

```python
plan = load_plan("plans/hill_climb_full.yaml")
result = Runner(plan, station, frames, {"monitor": monitor}, log).run()
abandoned = [stage.name for stage in result.stages if stage.abandoned]
```

The match plans use 300 seconds, with the last five reserved for requesting stop. The runner starts its clock after preflight. Match procedure still needs to align this start with the organizer's go signal. A designated team member can call stop.

## Shape

`Plan.match: MatchRules | None` enables the match clock and validates the named unplug and stack gates. Required stages run in plan order and halt on exhaustion. `Stage.stage_budget_s` caps total work, including retries and resets. `on_fail: abandon` marks an optional stage. Its `reserve_after_s` protects time for later stages. A dependent optional stage only runs after its prerequisite passes. The runner records abandonment separately from success and continues to the next eligible stage.

The runner checks the remaining budget before commands, when it sleeps or polls, and after a verifier returns. A timed-out command is ambiguous and terminates the run. The station's reply is separate from the stop request. HTTP timeouts are socket bounds. Physical stop and command ordering after a network failure depend on the station.

The unplug gate needs visual evidence of a cable clear of the hub. Rubric v4 requires a stack at least four inches tall that stands freely for three seconds after release. Current camera evidence and monitor prompts are proxies for the judge. Hardware validation needs a height reference and a check that the release and three-second dwell are visible.

## Design selection

The design review preferred a separate hierarchy with typed proof and action leases for a later version. The first slice keeps the existing runner because it already owns prompt changes, resets, and stop. The separate controller would need those paths extracted before it could run a match. This slice borrows explicit gate roles, an absolute clock, and separate abandonment and stop outcomes. It keeps generic plans and the legacy immediate `skip` behavior.

## Evidence and next tests

REFLECT uses observations around a failed subgoal to choose a bounded correction. Inner Monologue shows how false success can lead planning astray. LIBERO-RECOVER separates a retry from restoring a disrupted scene. Those distinctions map to stage verdicts, the authored recovery menu, and bounded abandonment. [REFLECT](https://proceedings.mlr.press/v229/liu23g.html) · [Inner Monologue](https://proceedings.mlr.press/v205/huang23c.html) · [LIBERO-RECOVER](https://arxiv.org/abs/2609.05178)

IntervenGen supports labeling mistakes and their corrections separately in future demonstrations. FORGE uses estimated Cartesian contact force and an impedance controller. Gripper motor torque is a separate observation and needs a bench calibration before it can support any insertion judgement. [IntervenGen](https://doi.org/10.1109/IROS58592.2024.10801523) · [FORGE](https://doi.org/10.1109/LRA.2025.3551637)

Sentinel supports comparing timestamped observations asynchronously. Hi Robot separates short task commands from the controller that executes them. Use a fake clock and scripted station to check that late verdicts never unlock another task, recovery consumes the stage budget, and optional failure preserves verified core progress. [Sentinel](https://proceedings.mlr.press/v270/agia25a.html) · [Hi Robot](https://www.pi.website/research/hirobot)

## LiveKit

Rubric v4 awards 10 points when the team shows its use of LiveKit to the referee before the match. The same rubric restricts human input after go, including voice. Keep tele-op handoffs in practice and demonstration collection. [Event page](https://luma.com/pah)

For training, Portal can record synchronized observations, executed actions, and which operator supplied each action. Use the capture timeline to label the policy mistake, human correction, and recovery result. Verify the event's Metal/Dream adapter, feature schema, and Dream import against a recorded sample before relying on this path. The public Portal HITL tutorial uses a different arm and an ACT policy. [LiveKit Portal](https://github.com/livekit/portal) · [HITL reference](https://github.com/livekit-examples/portal-hitl)

For detection, the optional LiveKit observer subscribes to named camera tracks and can run the existing monitor for a selected stage. It logs locally received frames and advisory verdicts. Comparing view coverage and detection latency with Dream debug trips requires paired recordings with a shared capture clock. The runner retains control and task advancement. [Robot camera tracks](https://docs.livekit.io/robotics/media/video/video-tracks/)

# Hill Climb harness

A supervisor that runs Dream-1 through a long-horizon task as a sequence of stages. For each stage it
gives the model a prompt, watches the cameras, decides whether the stage worked, and recovers (re-prompt,
home and retry, skip, or abort) when it did not. Every decision goes to `runs/<timestamp>/events.jsonl`
with the camera frames it looked at.

Python 3.12+, stdlib + PyYAML only. The design contract is `DESIGN.md`.

## Safety model

- **It never touches a motor.** It has no robot driver, no joint commands, no camera drivers. It only
  calls Dream's own station agent over HTTP on 127.0.0.1 (`/status`, `/start`, `/stop`, `/home`, `/reset`,
  `/prompt`) and reads frames from the debug view. Every speed cap, clamp, gripper force cap and home move
  stays in Dream's control loop.
- **Preflight refuses** to start if the station is not idle, an arm is dead, or a camera is stale (> 2 s).
- **Fails safe**: an arm dying, the station entering `error`, the time budget, Ctrl+C, or `s` + Enter all
  send `POST /stop` (the arms hold where they are). It never homes at the end; you do that.
- `--dry-run` sends no POST at all; `--live` makes you type `yes` after the safety lines.
- The physical e-stop is still the real safety. Keep your hand on it.

## Run it (on the station)

```bash
source ~/dream-env/bin/activate
dreamcli robot up --view-port 8093            # YAM fine-tune: dreamcli robot up joint --view-port 8093

python -m harness plans/example_hill_climb.yaml --dry-run    # reads status/frames, prints what it would POST
python -m harness plans/example_hill_climb.yaml --live       # hand on the e-stop, people clear; type yes

dreamcli robot down                                          # at the end
```

Keep the `dreamcli robot up` terminal running; run the harness in a second terminal (also with the
`dream-env` activated). Options: `--station URL` (default `http://127.0.0.1:8091`), `--view URL`
(default `http://127.0.0.1:8093`), `--runs-dir DIR`, `--verifier manual|claude|time` (override every stage).

While running, type `y` / `n` + Enter to answer a manual verifier, `s` + Enter to stop.

Offline practice, no station needed: `python -m harness plans/example_hill_climb.yaml --mock
[--scenario happy|arm_dies|start_error|slow_start|camera_stale]` (uses `fake_station.py`). Manual stages
wait for your keypresses; add `--verifier time` to let it run unattended.

## Test in simulation

`sim_station.py` is a stand-in for the station agent that drives Dream's own MuJoCo YAM simulator
(`dream_examples/yam_mujoco`), with the same HTTP routes on 8091 and the same debug view on 8093. The harness
cannot tell the difference, so you can test a plan end to end, with the real Dream-1 model, before the robot.
It uses Dream's own control loop (camera windows, `get_action`, `validate_chunk`, 20 Hz stepping), so nothing
physical is involved and `--live` is safe to confirm.

On a laptop with the `dreamlabs` library installed and your Dream API key saved (`~/.dreamlabs/credentials`,
from the Getting started page):

```bash
# terminal 1: the simulated station (real Dream-1, real time)
python sim_station.py --policy dream [--checkpoint dream-1-ft:...]

# terminal 2: the harness against it
python -m harness plans/sim_fruit_bowl.yaml --live --station http://127.0.0.1:8091 --view http://127.0.0.1:8093
```

`plans/sim_fruit_bowl.yaml` has three stages for objects in the sim scene (apple, orange, banana, a bowl and a
blue plate). The verifier is `manual`: watch the saved frames in `runs/<timestamp>/` or the `/trip/<n>` frames
on 8093, or run with `--verifier time` to let it run unattended. If Dream's example is not under
site-packages, add `--example-dir PATH/TO/dream_examples/yam_mujoco`. `--no-realtime` runs the sim as fast as it
renders.

Offline, no key and no network: `python sim_station.py --policy scripted` returns small sinusoidal joint chunks
of the right shape, so the harness, the state machine and the frames can be tested anywhere that has
`pip install mujoco pillow numpy`. On a headless Linux box set `MUJOCO_GL=egl` (needs a GPU) or
`MUJOCO_GL=osmesa` (software; `apt install libosmesa6`), which is the automatic default there. Software
rendering is slow (about 5 s per chunk), so use long stage timeouts or `--verifier time`.
`pytest tests/test_sim_station.py` covers the scripted mode and skips itself without mujoco.

## Writing a plan

```yaml
task: "clear the table into the bin"      # for logs
checkpoint: null                           # dream-1-ft:... or null for base Dream-1
time_budget_s: 900                         # whole run
check_every_s: 3.0                         # how often a verifier is asked
verifier: manual                           # default: manual | claude | time
cameras_for_check: [scene]                 # optional: roles a verifier sees (substring match), default all
stages:
  - name: pick_red                         # unique
    prompt: "pick up the red cube"         # one line, <= 512 chars; sent to the model as-is
    success: "Is the red cube held in a gripper, off the table?"   # yes/no question for the verifier
    timeout_s: 60                          # attempt fails after this
    max_attempts: 3
    min_run_s: 4                           # no verifier call before this
    verifier: manual                       # optional per-stage override
    recovery:                              # prompts tried in order on attempt 2, 3, ...
      - "open both grippers and move the arms up"
    on_fail: home_and_retry                # retry_in_place (default) | home_and_retry | skip | abort
```

Stages run back to back; between stages the harness changes the prompt live (`/prompt`) with no stop.
`retry_in_place` runs the recovery prompt for `min(timeout_s/2, 20)` s and then the stage prompt again;
`home_and_retry` does stop, home, start. Out of attempts: `skip` moves on, anything else fails the run.
Bad plans are rejected with the stage and field named.

## Verifiers

- `manual` (default): you watch the robot; `y` = stage done, `n` = attempt failed now.
- `time`: for stages with no check; done after 90% of `timeout_s`.
- `claude` (optional): sends the camera frames and the stage question to the Anthropic API
  (`claude-haiku-5-5` by default) and needs `ANTHROPIC_API_KEY` in the environment. The key is only sent to
  api.anthropic.com and is never logged or printed. A stage counts as done only for `done: true` with
  confidence >= 0.7. **Using an external model as a judge may not be allowed by the event rules. Check with
  the organizers before using it.** Use `manual` if unsure.

- `claude+manual`: Claude judges every check, and your `y` / `n` overrules it. Run with
  `--verifier claude+manual`. Good for practice runs: you watch Claude's calls in `events.jsonl` and correct them.

## Logs

`runs/<UTC timestamp>/` holds `events.jsonl` (one JSON event per line), `<seq>_<tag>_<role>.jpg` frames the
verifier saw, and `summary.json`.
